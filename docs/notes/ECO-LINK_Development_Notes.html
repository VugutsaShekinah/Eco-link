What we built

Viva questions & model answers

Q1. Why did you build a custom User model instead of using Django's default?

Because the system logs in by email and needs a role and an eco-points balance on every user. Django's default user logs in by username and has no such fields, so I extended AbstractUser, removed username, made email the login field, and added role, status, and eco_points_balance.

Q2. What is a migration?

A migration is a Python file Django generates from my models that describes the exact database changes to make. makemigrations writes it; migrate runs it against PostgreSQL to create or alter tables.

Q3. Why is the database password not in your code?

It lives in a .env file that is listed in .gitignore, so it never reaches GitHub. settings.py reads it at runtime with python-dotenv. This is a security best practice and directly supports the report's "Private/Accountable" RAPID goals.

Q4. What does the custom UserManager do?

It teaches Django how to create users and superusers using an email as the identifier instead of a username - normalising the email, hashing the password, and setting sensible defaults (e.g. a superuser gets the Administrator role).

Q5. What is role-based access control here, at the model level?

Every user carries a role field (Student, Staff, Community, Administrator). Later views check this - the is_administrator property is a convenience for those checks - so only administrators can reach admin-only pages.

Key points to remember

  • 6 models total will exist: User, DropOff, Hub, Reward, Redemption, Manufacturer.
  • Stack: Python 3.14, Django 5.2 LTS, PostgreSQL 18, Bootstrap 5, Git.
  • Eco-points rule (coming up): 10 points per kg, awarded only after an admin verifies a drop-off.

Viva questions & model answers

Q1. Walk me through what happens when a user registers.

They pick a role tab, fill name/email/password and submit a POST with a CSRF token. The RegistrationForm validates it (unique email, matching strong passwords, allowed role). On success it saves the user with the password hashed, logs them in, and redirects to the dashboard. On failure the page re-renders with error messages.

Q2. How do you stop someone registering as an Administrator?

The form's role field only offers the three public roles, so any other value fails validation on the server - not just hidden in the UI. Admins are created by existing admins through the Django admin instead.

Q3. What is CSRF and how do you protect against it?

Cross-Site Request Forgery tricks a logged-in user's browser into submitting a request they didn't intend. Django's CSRF middleware plus the {% csrf_token %} tag put a secret token in every form and verify it on submit, so forged requests are rejected.

Q4. How does login redirect work?

@login_required and LOGIN_URL send anonymous users to /login/; after a successful login Django redirects to LOGIN_REDIRECT_URL (the dashboard). It's all driven by URL names, so paths aren't hard-coded.

Q5. Why reuse Django's built-in Login/Logout views?

They already handle sessions, security, and edge cases correctly. Re-writing that by hand would be error-prone. We only customised the form (to use email) and the template.

Key points to remember

  • Role tabs = UI; the form field is the real gate. Validate on the server, always.
  • Login is by email; the login form's field is named username internally but accepts the email.
  • Tested: register, duplicate-email, admin-block, email login, logout, auth guard (6/6 pass).

Viva questions & model answers

Q1. What is a ForeignKey and why did you use one here?

It's a link between rows. Each Hub can be collected by one Manufacturer, and one Manufacturer can serve many Hubs - a one-to-many relationship - so Hub holds a ForeignKey to Manufacturer.

Q2. What does on_delete=SET_NULL do, and why not CASCADE?

If a manufacturer record is deleted, SET_NULL just clears the link on each hub and keeps the hubs. CASCADE would delete the hubs too, which would be wrong - the physical collection points still exist even if we drop a recycler.

Q3. Why DecimalField for capacity instead of a normal number?

Because weights need exact precision. Floating-point numbers introduce tiny rounding errors, which is unacceptable when they feed into eco-point calculations. Decimal stores the exact value.

Q4. What is a migration?

A migration is an auto-generated, version-controlled Python script describing a database change. makemigrations creates it from my models; migrate applies it. It lets the schema evolve safely and be reproduced on any machine.

Q5. How do administrators manage hubs?

Through the Django admin. I registered both models with ModelAdmin classes that add search, filters, and inline status editing, so an admin can create a hub, set its capacity, assign a recycler, and flip its status without writing any code.

Key points to remember

  • Hub fields = name, location, capacity_kg, status, manufacturer(FK) - straight from the ERD.
  • Manufacturers are external stakeholders: stored and managed, but they don't log in (§1.5).
  • is_accepting is a property = True only when status is Active (used when logging drop-offs next).
  • Tested: str output, defaults, is_accepting, capacity validation, SET_NULL (7/7 pass).

Milestone 3 - Drop-offs & Eco-points DONE

This is the heart of ECO-LINK and your Specific Objective 2. Expect the most viva questions here.

What we built

  • DropOff model - one plastic deposit: user, hub, plastic type, weight, status, timestamps.
  • One shared points formula (10 points/kg) used by the model, the view, and the JS preview.
  • Live JavaScript preview - shows points as you type the weight, before submitting.
  • Verification signal - awards points automatically the moment an admin verifies a drop-off.
  • Dashboard + history pages showing real balance and drop-offs.

The golden rule: points only on verification

Log drop-off -> status = PENDING (0 points yet) | admin verifies it v status = VERIFIED | post_save signal fires v user.eco_points_balance += weight x 10 verified_at = now (audit trail)

Pending drop-offs never count toward the balance or leaderboard. This is the report's "Accountable" RAPID principle - every point has a verified record behind it.

Viva questions & model answers

Q1. How are eco-points calculated and why one formula in one file?

10 points per kilogram, defined once in points.py. The model, the view message, and the JavaScript preview all use that same rate, so the number a user previews always matches what they're eventually credited. This is the RAPID "Responsible" principle - one rule, applied consistently.

Q2. What is a Django signal and why did you use one here?

A signal runs code automatically after an event - here, post_save on DropOff. When a drop-off becomes Verified, the signal adds the points to the user's balance. Using a signal means verification works identically whether it happens through the admin or anywhere else in code.

Q3. How do you prevent awarding points twice?

The signal only awards when the status is Verified AND verified_at is still empty. After awarding, it stamps verified_at, so any later save is ignored. That makes it idempotent.

Q4. Why don't pending drop-offs count?

To keep the system trustworthy and accountable. An administrator checks the physical weight at the hub before verifying, so points always correspond to a real, confirmed deposit - the audit trail behind every eco-point.

Q5. How does the live points preview stay accurate?

The template passes the same rate the server uses into a small JavaScript function that multiplies weight by that rate as the user types. Because both sides use one rate, the preview can't disagree with the final award.

Q6. Why PROTECT on the hub foreign key but CASCADE on the user?

Deleting a user removes their own drop-offs (CASCADE). But a hub with recorded drop-offs is part of the history, so PROTECT stops it being deleted and silently wiping verified contributions.

Key points to remember

  • Rate = 10 points/kg, one place (points.py).
  • PENDING -> VERIFIED is the only path that awards points (via the signal).
  • Signal is idempotent (the verified_at guard) - no double points.
  • Admin verify action must loop save(), never bulk update().
  • Tested hard: formula, award-once, accumulation, weight validation, view + closed-hub guard (9/9).

Milestone 4 - Rewards & Redemption DONE

What we built

  • Reward model - catalogue items with a points cost (vouchers, certificates...).
  • Redemption model - a record of a user spending points on a reward.
  • Redeem flow - checks the balance, deducts points, records the transaction - safely.

Why it's needed

  • Completes the incentive loop: earn points (drop-offs) then spend them (rewards) - §3.2.3.3.
  • Rule: redeem only if balance >= points_required, then deduct.

Redeem flow (earn vs spend)

EARN (Milestone 3) SPEND (Milestone 4) verified drop-off click Redeem (POST) balance += pts | balance >= cost ? --no--> error, no change | yes v balance -= cost create Redemption record

Viva questions & model answers

Q1. How do you stop a user redeeming points they don't have?

The redeem service runs inside a database transaction and locks the user's row with select_for_update(). It re-reads the balance, checks it against the cost, and only then deducts and records the redemption. The lock means two concurrent redeems can't both pass the check.

Q2. What is a database transaction and why use one here?

A transaction groups several database operations so they either all commit or all roll back. Deducting points and creating the redemption record must happen together - a transaction guarantees we never deduct without recording, or record without deducting.

Q3. Why is redeeming POST-only?

Because it changes data (spends points). GET requests should be safe and repeatable; if redeem were a normal link, a browser prefetch or refresh could spend points by accident. @require_POST plus a form with a CSRF token enforces this.

Q4. Why store points_spent on the Redemption instead of reading the reward's cost later?

It's a historical snapshot. If an admin later changes a reward's price, past redemptions should still show what was actually spent. Storing the value at redeem time keeps history accurate.

Q5. Why is the Redemption admin read-only?

Redemptions are financial-style records created only by the redeem flow. Letting an admin hand-create one would record a spend without actually deducting points, corrupting balances. So add is disabled and the fields are read-only.

Key points to remember

  • Redeem = atomic transaction + row lock + check + deduct + record.
  • Earn via signal, spend via service - each matches how the action happens.
  • POST-only + CSRF for anything that changes data.
  • Tested: deduct, insufficient blocked, exact balance, inactive reward, login, POST-only (7/7).

How "eco-points awarded" is calculated

points_awarded = SUM(all user balances) + SUM(all points spent) = points still held + points already redeemed = every point ever awarded (gross)

This is exact and cheap - two simple database sums, no row-by-row looping.

Viva questions & model answers

Q1. How are the dashboard statistics calculated?

Live, using Django ORM aggregates - Count for totals and Sum for kilograms and points. Nothing is cached or stored, so every figure reflects the current database state the moment the page loads.

Q2. How do you stop non-admins seeing the dashboard?

Every dashboard view uses the admin_required decorator. It checks the logged-in user's role; anonymous users go to login and non-admins are redirected to their own dashboard - even if they type the URL directly.

Q3. When an admin verifies a drop-off here, how are points awarded?

The view just sets the status to Verified and saves. The Milestone 3 post_save signal does the awarding. The dashboard reuses that one rule rather than duplicating it, so verification behaves identically wherever it happens.

Q4. Why compute points awarded as balances plus points spent?

Because a user's balance is points awarded minus points spent. Adding the total spent back gives the gross total ever awarded, using two cheap database sums instead of recalculating from every drop-off.

Q5. Why is changing an administrator's status blocked?

To prevent an admin accidentally suspending another admin (or themselves) and locking the team out of management. The view rejects status changes on administrator accounts.

Key points to remember

  • Stats are live ORM aggregates (Count/Sum) - never stored counters.
  • Verify reuses the Milestone 3 signal - one awarding rule everywhere.
  • admin_required guards every view; admins can't be edited here.
  • Tested: access control, stats, verify+award, POST-only, status change (8/8).
